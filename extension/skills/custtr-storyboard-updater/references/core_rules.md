# Core Rules

These rules mirror the active `SKILL.md` rule set and are non-negotiable for every run.

1. **Audit before editing.** Collect authoritative sources for the deck's claim clusters and read all user-provided material (PDFs/docs/links/notes/constraints) before making any planning decisions. See "Source Collection Requirements" and "Mandatory Workflow" Phase 2.
2. **Build a story model before planning.** Explicitly identify the primary message, objectives, key talking points, flow, assessment points, and summary claims.
3. **No isolated keyword slides.** New source deltas must be mapped to objectives, body content, knowledge checks, summary, and narrative flow before any slide is added.
4. **Plan before mutation.** Generate an update plan and get user approval before writing an updated deck.
5. **Execution order is fixed:** update existing content, remove obsolete content, then add new slides if needed.
6. **Do not directly insert cloned slide XML.** New slides must be created as a standalone PPTX and merged by range using `psas-pptx-merger`.
7. **New slides are LLM-authored, not pipeline-routed.** Each `add_new_slide` action describes instructional intent, visible content, visual approach, source basis, notes, and QA expectations. The LLM chooses how to construct the slide so it matches the existing deck. Do not route new slides through fixed layout-generation scripts or external templating backends.
8. **Existing-slide edits are marked, but must remain readable.** Apply OOXML change marking from `references/ooxml-highlight-position.md` for existing-slide OST edits. Use the smallest readable marked change that communicates the update: `fragment_replace` for small terms/values, `update_existing` only when the marked full-shape replacement will still read cleanly, and redesigned existing-slide or `add_new_slide` actions when a dense table, diagram, knowledge check, or long bullet rewrite would become visually noisy.
9. **New slides are not edit-highlighted by default.** Add badges, update callouts, or other visible review cues only when they fit the deck's authoring style and improve comprehension. New slides must instead pass XML/package QA and read as polished training content, not as a diff artifact.
10. **Narrative notes are first-class content.** Every slide â€” new or updated â€” must have full narration. See "Narrative Notes" below.
11. **Knowledge checks and summaries must be updated** when newly inserted content changes what learners should know.
12. **Do NOT remove authoring markers.** Labels like `Fully Shared Slide`, `Partially Shared Slide`, and `Slide-*` numbering are used by developers working on the decks downstream. Leave them exactly as they are.
13. **Never remove the trailing AMD logo slide.** The last slide in every deck carries the AMD logo and exists for legal/compliance purposes. It may look blank or decorative, but it must always remain as the final slide in the output.
14. **Never conclude "no changes needed" without evidence.** A deck that truly needs zero updates is rare. If the cross-validation audit finds nothing, present the source inventory and cross-validation report to the user and ask them to confirm. The default assumption is that something needs updating â€” the burden of proof is on "no changes needed", not on "changes needed".
15. **Audit on two axes, every slide, no exceptions.** Every slide must be examined against **Axis A** (topic deltas from the source inventory) **and** **Axis B** (staleness deltas from the per-deck `stale_terms.json` artifact authored from sources â€” see `references/stale_terms_schema.md`), regardless of whether the slide's title matches the deck's theme. The cross-validation report must list every slide in either `slides_with_findings` or `slides_explicitly_cleared` (with a reason). A slide may not be silently skipped because its topic looked off-theme. See Phase 3.
16. **Group-nested shapes are the most common audit miss.** Diagram boxes are almost always children of a `<p:grpSp>` group. `extract_deck.py` flattens groups so every shape appears in `slide['texts']`, but the visible diagram label is just another shape â€” it must be audited like any other. If the only audit hits on a slide are titles and body bullets but the slide has a diagram, the audit is incomplete.
17. **Scope phrase + stale-term specifics on the same slide = advisory lint.** A slide whose title, OST, or body uses a portfolio-scope phrase from `stale_terms.json` (e.g. "Versal Adaptive SoC", "Versal architecture") without an explicit `Gen 1`/`Gen 2` qualifier and also carries stale-token specifics must receive LLM disposition: confirmed finding, source-backed clear, plan action, or intentional exception.
18. **Mechanical gates are non-negotiable.** Phase 3 produces `stale_term_scan.json` and `scope_consistency.json`, then runs `audit_gate.py --stage pre-plan` before the user checkpoint. Phase 4.5 runs `validate_plan.py` and `audit_gate.py --stage pre-execute` before any deck mutation. After apply, `post_apply_check.py` re-scans the produced deck and refuses merge if a promised replacement silently failed (e.g. `match_text` typo or whitespace drift).
19. **Staleness is per-deck, authored from sources â€” never carried over.** Each run produces `<work_dir>/stale_terms.json` (schema: `references/stale_terms_schema.md`). The LLM authors it during Phase 2 from the live source inventory and the deck's own content. Entries carry `skip_if_preceded_by` / `skip_if_followed_by` guards so context-correct legacy mentions (e.g. `CPM5 CCIX`) do not trigger false findings. The previous global cheat-sheet (`versal_gen1_vs_gen2_ip_delta.md`) is **gone**: copying a previous deck's staleness list is forbidden because it bakes in context-dependent assumptions.
20. **Speaker notes use verbatim `old_speaker_notes`.** For every `notes_update` action, `old_speaker_notes` must be the literal original speaker-notes text extracted from `ppt/notesSlides/notesSlideN.xml`. Never `""`, never paraphrased, never omitted. `deck_extract.json` does NOT include speaker notes â€” run `scripts/extract_speaker_notes.py` in Phase 1.5 to populate `original_notes.json`, and copy from there. Setting `old_speaker_notes=""` while the deck has real notes produces an all-yellow notes pane (pure-insertion diff), which looks like a complete rewrite to the learner and is not acceptable as instructional narration.
21. **Speaker-notes edits default to `notes_changes` (surgical), not `speaker_notes` (wholesale).** When extending or correcting an existing notes block, the action MUST use `notes_changes: [{match_fragment, replacement_fragment}]` to express per-paragraph diffs. Author the replacement text as clean narrator-ready prose: concise, current, source-backed, and readable if an instructor reads it verbatim. Wholesale replacement via `old_speaker_notes` + `speaker_notes` destroys multi-paragraph structure and is rejected by `audit_gate.py`'s notes-structure sweep. Current tooling may still render `notes_changes` with diff-style marking; do not rely on that marking as the teaching surface, and do not claim clean notes are enforced unless the scripts have been changed.
22. **Narrator-script style â€” no meta-narrative openers.** Speaker notes must open with substantive content (a fact, definition, or recommendation). The following openers are banned in every note, on every slide: *"On this slide..."*, *"On the previous slide..."*, *"This slide..."* / *"These slides..."*, *"To recap..."*, *"This is the knowledge check..."*, *"Here we see..."* / *"Here we have..."*, *"In this section..."*. An instructor reading the deck verbatim should sound like a narrator, not like a screen-reader.
23. **Content-level cross-validation, not substring-level.** A clean stale-term scan is necessary but not sufficient. A slide may only be marked `explicitly_cleared` when the LLM verifies its claim clusters against cited source text and no source contradicts the slide. The old "no stale-term hits -> cleared" shortcut is removed.
24. **Knowledge-check slides get a dedicated audit pass.** For every slide whose title matches `Apply Your Knowledge | Knowledge Check | Quiz | Review Question`, re-read every option and the marked-correct answer, then confirm the answer set is still exhaustive and correct given any content added elsewhere in the deck. If new tech has been added to the module's scope (e.g. CPM6 -> PCIe Gen 6 -> 64 GT/s), either expand the answer set or re-scope the question, and update the correct/incorrect feedback in the speaker notes in sync.
25. **Advisory source-gap lint during validation.** Phase 2 source collection is the starting set, not the complete set. `detect_source_gaps.py` emits claim-token lint signals that may guide targeted source gathering, but the LLM must judge source-to-claim entailment. Cap source follow-up at 1 round per slide; after one round, batch-escalate unresolved evidence gaps to the user.
26. **Pre-merge file-lock check; validate-freshness guard.** Before running `merge_storyboard.py`, test-write a sentinel byte to the target output path. If the file is locked (typically: open in PowerPoint), stop and tell the user to close the deck. `validate_deck.py` and `post_apply_check.py` must abort if `merge_storyboard.py` exited non-zero, instead of silently running against a stale prior artifact. Treat a successful validate against an old file as a worse failure than a clean error.
27. **Mechanical sweeps run before execution.** `audit_gate.py` runs (a) the **version sweep** - every `YYYY.N` token must equal `target_release` or appear in an explicit exception; the title-slide version is an error, not a warning; (b) the **summary/recap sweep** - every summary slide must be reviewed or updated; (c) the **notes-structure sweep** - any existing-slide action using wholesale `speaker_notes` instead of `notes_changes` is rejected; (d) the **notes-OST coherence sweep** - any `notes_update` action that introduces technical terms not present in the slide's OST or a companion OST action is rejected; (e) the **new-slide intent and XML/package-QA sweep** - every `add_new_slide` action must describe visible content, visual approach, QA expectations, source basis, and speaker notes without requiring a fixed layout schema; (f) the **OST-review completeness check** - every `notes_update` action must carry a valid `ost_reviewed` value. These gates prevent many stale or unsupported changes, but they are not a substitute for a human/LLM readability review of marked slides, dense tables, diagrams, knowledge checks, or speaker notes through extracted text and OOXML inspection. Heuristic sweeps produce advisory lint unless confirmed by LLM-authored verification artifacts.
28. **Structural completeness â€” parallel sections need LLM parity review.** When the deck dedicates a section to teaching concept X, and concept Y is a peer of X in the same conceptual grouping, Y must receive comparable depth or a documented exclusion. The grouping emerges from the deck's own content structure and the source inventory. Advisory parity scripts can surface candidates, but the LLM decides whether the right action is a new slide, an existing-slide update, or an out-of-scope rationale.
29. **Summary slides must reflect the complete updated story.** After all content changes are planned (including new slides), re-read every summary/recap/key-takeaways slide and verify that its claims, bandwidth figures, protocol lists, and feature highlights cover the full scope of the deck â€” including newly added content. A summary that was correct before new slides were added is stale after them. Every `add_new_slide` action that introduces a new capability (new protocol, new bandwidth tier, new IP block) must trigger a dependent `update_existing` action on the nearest summary slide, or the plan is incomplete.
30. **"No feature changes" does not mean "no content changes needed."** A source that says "no feature changes between version X and version Y" confirms that existing claims remain correct â€” it does NOT justify skipping content gaps. A topic that exists in the product but is absent or under-represented in the deck is a content gap regardless of whether it changed between releases. Separately evaluate: (a) are existing claims still correct? (b) is the topic adequately taught? Both must be true to clear a slide.
31. **Decompose every source delta into independently teachable concepts.** Before plan authoring, every source delta must be broken into its constituent concepts. A "source delta" is a change or addition from a source (e.g. "CPM6 added to Versal Premium Gen 2"). A "teachable concept" is a topic a learner would need a distinct explanation of. For each concept, record: (a) `concept`, (b) `parent_delta`, (c) `independently_teachable`, (d) `current_coverage`, (e) `adequate`, and (f) recommended LLM disposition. Concepts tagged `independently_teachable: true` AND `adequate: false` require explicit disposition, not automatic slide creation.
32. **Source deltas may introduce concepts that belong to categories not yet present in the deck.** A delta about controller X may introduce protocol Y, transceiver family Z, or security capability W. Each concept must be assessed in its own natural category, not constrained to the category of its parent delta. If the concept would create a new section that does not yet exist in the deck, that is a `new_slide_candidate` finding. Do not assume the deck's current section structure is complete â€” source deltas can reveal structural gaps.
33. **Parallelism is optional and conditional.** Use concurrent tool calls or subagents for expensive independent retrieval or generation when outputs are independent and shared reasoning context is not harmed. Do not parallelize tightly coupled semantic work merely to satisfy process ceremony.
34. **Speaker notes must not be the sole teaching surface for any new concept.** Notes elaborate, explain, and provide context for what is visible on screen - but they must not introduce a technical concept (protocol, IP block, spec, capability) that has zero corresponding mention in the slide's on-screen text (OST). If a `notes_update` action introduces key terms that do not appear in either the existing OST or a planned OST-level action (`update_existing`, `fragment_replace`, `add_new_slide`) on the same slide, the plan is incomplete. `audit_gate.py` enforces this: for every notes-modifying action, it extracts technical terms from the replacement/new notes text and verifies each appears in the slide's current OST shapes or in a companion OST action targeting the same slide. A finding that says "slide only covers X - no mention of Y" is not adequately addressed by adding Y to the notes alone. The OST must at least reference Y (a bullet, a label, a callout, a table row) so learners see the concept before the instructor elaborates on it.
35. **Intra-slide term consistency â€” diagram labels must match bullet text and source canonical forms.** For every slide that contains both bullet/body text and diagram/grouped-shape labels, every technical term (processor name, IP block name, protocol name, interface name) must be consistent across all shapes on that slide. A bullet saying `A78AE` while a diagram label says `A78E` on the same slide is a high-confidence inconsistency signal and should become a finding when confirmed against the slide and canonical source form. This is enforced mechanically: `consistency_scan.py` (run automatically by `storyboard_update.py --mode audit-plan`, written to `consistency_scan.json`) detects near-miss technical-token variants that differ only by an internal letter edit (e.g. `A78AE` vs `A78E`) while ignoring legitimate generation siblings that differ only by digits (e.g. `CPM5` vs `CPM6`, `DDR4` vs `DDR5`). Every non-advisory violation must be reconciled before the pre-plan gate passes â€” represented by a verification finding, addressed by a plan action, or explicitly cleared with a reason that names one of the implicated tokens. `audit_gate.py` rejects unreconciled violations. This check runs during Phase 3, not as a post-apply gate, so the typo is caught before it ships. A clean per-slide LLM read is necessary but not sufficient: the mechanical scan exists because batch-clearing a slide as "already the target generation" silently shipped a one-letter label typo in a real run.
36. **Before authoring any JSON artifact, read `references/artifact_schemas.md` â€” specifically the field-name quick reference table at the very top.** Never write field names from memory: `slide` is wrong, `slide_number` is correct; `action_type` is wrong, `type` is correct; `match` is wrong, `match_text` is correct â€” and so on for every alias in the table. This applies equally to subagents: every Agent tool prompt that asks for a JSON artifact **MUST** include this instruction verbatim: *"Read `references/artifact_schemas.md` field-name table before writing any JSON. The table is at the top of the file."* Subagents start with no parent context and will invent field names without this explicit instruction.
37. **A clean stale-term scan (0–3 hits) is advisory lint.** On large decks, a low stale-term hit count is a signal to review `stale_terms.json` scope and claim/source dispositions — not a hard failure and not a reason to pad stale terms or plan actions to satisfy a count. `audit_gate.py` emits warnings for suspiciously shallow counts; the LLM must confirm coverage rather than treat a clean scan as proof of completeness.
38. **Every `notes_update` action requires an explicit OST review outcome.** When speaker notes are updated on an existing slide, the author must document whether the on-screen text (OST) of that slide also needs updating. Set `ost_reviewed` on the action to one of two values: `"consistent"` â€” the existing OST already reflects the notes change; no OST action is needed. A non-empty `ost_review_note` explaining the alignment is required. `"companion_action_added"` â€” a companion `update_existing` or `fragment_replace` action targeting the same `slide_number` is present in the plan to update the OST. `validate_plan.py` rejects any `notes_update` action missing `ost_reviewed`, carrying an invalid value, using `"consistent"` without `ost_review_note`, or claiming `"companion_action_added"` when no qualifying companion action exists. `audit_gate.py` additionally warns when `ost_reviewed: "consistent"` but the Phase 3 finding recommended an OST-level action â€” verify the OST is truly unchanged before marking consistent.

39. **Generational analysis is mandatory for every slide clear.** Before marking any slide as `slides_explicitly_cleared`, the auditor must document: (a) what generation the slide's content belongs to, (b) what changed between that generation and the target (with `source_ids`), and (c) why those changes do not affect this slide. Clearing reasons that only reference mechanical scan results (e.g. "no stale terms found", "scan is clean", "content is still valid") are rejected by `audit_gate.py`. The `generational_analysis` object is required on every `slides_explicitly_cleared` entry — see `references/artifact_schemas.md` for the schema. A slide whose content is factually correct but incomplete (e.g. describes CPM5 without mentioning CPM6) is NOT clear — it has a content gap finding.

40. **Portfolio-scope slides require IP-block-level source coverage.** When a slide is classified as an SoC overview, block diagram, or processing system diagram (typically 15+ shapes with named functional blocks), every functional block that carries a protocol name, spec value, or processor identifier is a key technical component to disposition against sources — not just blocks related to the deck's primary topic. The LLM may batch source queries and record which blocks changed, did not change, were unavailable, or are intentionally out of scope. A portfolio-scope slide cannot be cleared unless every named functional block on it has a source-backed disposition.

41. **Delta-tracing sweep — grep old spec values across all slides.** After Phase 2 source collection, for every source delta that identifies a changed specification (e.g. OCM 256 KB → 2 MB, line rate 32 GT/s → 64 GT/s, A72 → A78AE), grep `deck_extract.json` for the old value across ALL slides — not just slides thematically related to the delta's topic. A specification change discovered on one slide (e.g. slide 8 teaches OCM 2 MB) must be traced to every other slide that mentions the old value (e.g. slide 4 still says "256 KB"). Record each old-value hit as a candidate finding. This sweep runs during Phase 3, after the per-slide audit and before concept decomposition. It catches cross-slide inconsistencies that per-slide auditing misses because the auditor focused on the slide's primary topic rather than tracing every changed value deck-wide.

42. **Image-detection heuristic for OST review.** Before marking `ost_reviewed: "consistent"` on a `notes_update` action, verify that the slide's on-screen content is actually represented in `deck_extract.json` text shapes. If the speaker notes describe a table, diagram, or feature matrix but `deck_extract.json` shows fewer than 4 text shapes (excluding title, authoring markers, and slide-number labels), the visible content is likely an embedded image that the text extraction cannot see. In this case: (a) flag the slide as `image_limited` in the action's `ost_review_note`, (b) document which concepts from the notes update cannot be verified against OST because the OST is an image, and (c) add a `manual_review_required` note in the action specifying what the image should be checked for. Do NOT mark `ost_reviewed: "consistent"` with a generic note — the note must explicitly acknowledge the image limitation and list the unverifiable concepts. This prevents false "consistent" claims on slides where the real teaching content is baked into a non-editable image.

43. **Never write custom highlight code.** Import and call `add_highlight(rpr)` from `ooxml_helpers.py` for all highlight operations. OOXML requires `<a:highlight>` after `<a:effectLst>` and before `<a:uLnTx>`; PowerPoint silently ignores highlights placed elsewhere. `post_apply_check.py` validates highlight positioning and will flag violations.

44. **Mandatory user checkpoint between Phase 3 and Phase 4.** Present stale-term count, concept decomposition summary, parity matrix results, total findings count, and proposed plan scope in `$WORK/audit_summary.md` before writing `update_plan.json`. Do NOT proceed until the user explicitly acknowledges. See `references/workflow_phases.md` and `references/audit_summary_guide.md`.

45. **Scope-depth diagnostics are advisory.** `audit_gate.py` warns on suspiciously shallow stale-term, parity, concept, or action counts, while hard failures remain tied to evidence, schema, stale-hit reconciliation, notes, and package contracts.

46. **Stale-hit reconciliation is mandatory.** Every surviving entry in `stale_term_scan.json` must be represented by a verification finding, addressed by an update-plan action, covered by an `intentionally_kept` exception, or explicitly cleared with a token/location-specific reason. A slide with a surviving stale hit cannot be cleared by generic generational analysis alone.

47. **Cursor Plan mode is required before storyboard work.** If the current conversation is not already in Cursor Plan mode, immediately call `SwitchMode(target_mode_id="plan")` before any deck-update workflow step. Do not run source collection that creates artifacts, plan authoring, mutation, execution, or validation commands until the mode switch is accepted. This mode gate is separate from the Phase 3 to Phase 4 user checkpoint and approved `update_plan.json` requirement.

48. **Final PPTX validation is XML/package-only.** Never open generated or updated `.pptx` files in PowerPoint, LibreOffice, COM automation, browser UI, or any presentation viewer after merge. Updated decks may require PowerPoint repair, so final validation must inspect the PPTX as a ZIP/OOXML package: `validate_deck.py`, `post_apply_check.py`, `extract_deck.py`, direct `zipfile` reads, `ppt/slides/*.xml`, `ppt/notesSlides/*.xml`, relationships, `[Content_Types].xml`, and merge sidecars. Check text presence, notes presence, shape geometry values, relationships, slide order, stale tokens, highlight placement, authoring markers, and package structure through XML/package inspection.

## Theme Palette Extraction

Every new-slide authoring pass must inspect the base deck's visual system, including theme colors, fonts, spacing, and nearby slide patterns. Hardcoded generic colors, default python-pptx styling, and unreviewed visual output are hard failures at visual review. See `references/new_slide_guide.md`.
