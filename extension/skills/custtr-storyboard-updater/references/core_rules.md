# Core Rules

All 38 rules governing the storyboard update workflow. These are non-negotiable and apply to every run.

1. **Audit before editing.** Query MCP sources (NABU, Atlassian/Confluence, JIRA) and read all user-provided material (PDFs/docs/links/notes/constraints) before making any planning decisions. See "Source Collection Requirements" and "Mandatory Workflow" Phase 2.
2. **Build a story model before planning.** Explicitly identify the primary message, objectives, key talking points, flow, assessment points, and summary claims.
3. **No isolated keyword slides.** New source deltas must be mapped to objectives, body content, knowledge checks, summary, and narrative flow before any slide is added.
4. **Plan before mutation.** Generate an update plan and get user approval before writing an updated deck.
5. **Execution order is fixed:** update existing content, remove obsolete content, then add new slides if needed.
6. **Do not directly insert cloned slide XML.** New slides must be created as a standalone PPTX and merged by range using `psas-pptx-merger`.
7. **New slides use a structured layout routed to the correct pipeline.** Each `add_new_slide` action must specify a `slide_layout` and provide the layout-specific data. MARP-eligible layouts (`comparison_table`, `two_column`, `key_takeaway`, `cards`) are rendered via `create_marp_additions.py` (MARP + AMD theme + speaker-notes injection). Diagram layouts (`ascii_diagram`, `block_diagram`) are rendered via `create_additions_deck.py` (native PPT shapes). The plan JSON schema is identical for both â€” routing is by `slide_layout` value at execution time. See "Authoring New Slides" below.
8. **Existing-slide edits are marked.** Apply OOXML change marking from `references/ooxml-highlight-position.md`.
9. **New slides are not edit-highlighted.** The script adds a compact top-right yellow `New Slide` badge automatically.
10. **Narrative notes are first-class content.** Every slide â€” new or updated â€” must have full narration. See "Narrative Notes" below.
11. **Knowledge checks and summaries must be updated** when newly inserted content changes what learners should know.
12. **Do NOT remove authoring markers.** Labels like `Fully Shared Slide`, `Partially Shared Slide`, and `Slide-*` numbering are used by developers working on the decks downstream. Leave them exactly as they are.
13. **Never remove the trailing AMD logo slide.** The last slide in every deck carries the AMD logo and exists for legal/compliance purposes. It may look blank or decorative, but it must always remain as the final slide in the output.
14. **Never conclude "no changes needed" without evidence.** A deck that truly needs zero updates is rare. If the cross-validation audit finds nothing, present the source inventory and cross-validation report to the user and ask them to confirm. The default assumption is that something needs updating â€” the burden of proof is on "no changes needed", not on "changes needed".
15. **Audit on two axes, every slide, no exceptions.** Every slide must be examined against **Axis A** (topic deltas from the source inventory) **and** **Axis B** (staleness deltas from the per-deck `stale_terms.json` artifact authored from sources â€” see `references/stale_terms_schema.md`), regardless of whether the slide's title matches the deck's theme. The cross-validation report must list every slide in either `slides_with_findings` or `slides_explicitly_cleared` (with a reason). A slide may not be silently skipped because its topic looked off-theme. See Phase 3.
16. **Group-nested shapes are the most common audit miss.** Diagram boxes are almost always children of a `<p:grpSp>` group. `extract_deck.py` flattens groups so every shape appears in `slide['texts']`, but the visible diagram label is just another shape â€” it must be audited like any other. If the only audit hits on a slide are titles and body bullets but the slide has a diagram, the audit is incomplete.
17. **Scope phrase + stale-term specifics on the same slide = automatic finding.** A slide whose title, OST, or body uses a portfolio-scope phrase from `stale_terms.json` (e.g. "Versal Adaptive SoC", "Versal architecture") without an explicit `Gen 1`/`Gen 2` qualifier cannot also carry stale-token specifics on the same slide. `scripts/scope_consistency_scan.py` enforces this.
18. **Mechanical gates are non-negotiable.** Phase 3 produces `stale_term_scan.json` and `scope_consistency.json`. Phase 5 runs `audit_gate.py` and refuses to advance to apply unless every finding is either addressed by an action or explicitly cleared in `cross_validation_report.json`. After apply, `post_apply_check.py` re-scans the produced deck and refuses merge if a promised replacement silently failed (e.g. `match_text` typo or whitespace drift).
19. **Staleness is per-deck, authored from sources â€” never carried over.** Each run produces `<work_dir>/stale_terms.json` (schema: `references/stale_terms_schema.md`). The LLM authors it during Phase 2 from the live source inventory and the deck's own content. Entries carry `skip_if_preceded_by` / `skip_if_followed_by` guards so context-correct legacy mentions (e.g. `CPM5 CCIX`) do not trigger false findings. The previous global cheat-sheet (`versal_gen1_vs_gen2_ip_delta.md`) is **gone**: copying a previous deck's staleness list is forbidden because it bakes in context-dependent assumptions.
20. **Speaker notes use verbatim `old_speaker_notes`.** For every `notes_update` action, `old_speaker_notes` must be the literal original speaker-notes text extracted from `ppt/notesSlides/notesSlideN.xml`. Never `""`, never paraphrased, never omitted. `deck_extract.json` does NOT include speaker notes â€” run `scripts/extract_speaker_notes.py` in Phase 1.5 to populate `original_notes.json`, and copy from there. Setting `old_speaker_notes=""` while the deck has real notes produces an all-yellow notes pane (pure-insertion diff), which looks like a complete rewrite to the learner.
21. **Speaker-notes edits default to `notes_changes` (surgical), not `speaker_notes` (wholesale).** When extending or correcting an existing notes block, the action MUST use `notes_changes: [{match_fragment, replacement_fragment}]` to express per-paragraph diffs. Wholesale replacement via `old_speaker_notes` + `speaker_notes` destroys multi-paragraph structure and is rejected by `audit_gate.py`'s notes-structure sweep. Wholesale replacement is permitted only for true full-rewrite cases AND must carry the matching `notes_changes` field empty/absent reasoning in the action description.
22. **Narrator-script style â€” no meta-narrative openers.** Speaker notes must open with substantive content (a fact, definition, or recommendation). The following openers are banned in every note, on every slide: *"On this slide..."*, *"On the previous slide..."*, *"This slide..."* / *"These slides..."*, *"To recap..."*, *"This is the knowledge check..."*, *"Here we see..."* / *"Here we have..."*, *"In this section..."*. An instructor reading the deck verbatim should sound like a narrator, not like a screen-reader.
23. **Content-level cross-validation, not substring-level.** A clean stale-term scan is necessary but not sufficient. A slide may only be marked `explicitly_cleared` when (a) the stale-term scan is clean AND (b) every factual claim on it maps to at least one source in `reference_extract.json` AND (c) no source contradicts a claim. The old "no stale-term hits -> cleared" shortcut is removed.
24. **Knowledge-check slides get a dedicated audit pass.** For every slide whose title matches `Apply Your Knowledge | Knowledge Check | Quiz | Review Question`, re-read every option and the marked-correct answer, then confirm the answer set is still exhaustive and correct given any content added elsewhere in the deck. If new tech has been added to the module's scope (e.g. CPM6 -> PCIe Gen 6 -> 64 GT/s), either expand the answer set or re-scope the question, and update the correct/incorrect feedback in the speaker notes in sync.
25. **Recursive source gathering during validation.** Phase 2 source collection is the starting set, not the complete set. If any slide carries a factual claim with no matching source, Phase 2.5 (`detect_source_gaps.py` -> `coverage_gaps.json`) must trigger a targeted source-gathering sub-loop (NABU / Confluence / JIRA / web / user docs) and re-run the audit on the affected slide. Cap at 1 round per slide; after one round, batch-escalate all remaining unresolved gaps to the user in a single summary. See "Recursive Source Gathering" section.
26. **Pre-merge file-lock check; validate-freshness guard.** Before running `merge_storyboard.py`, test-write a sentinel byte to the target output path. If the file is locked (typically: open in PowerPoint), stop and tell the user to close the deck. `validate_deck.py` and `post_apply_check.py` must abort if `merge_storyboard.py` exited non-zero, instead of silently running against a stale prior artifact. Treat a successful validate against an old file as a worse failure than a clean error.
27. **Five mandatory sweeps run before plan approval.** `audit_gate.py` always runs (a) the **version sweep** â€” every `YYYY.N` token must equal `target_release` or appear in `intentionally_kept`; the title-slide version is an error, not a warning; (b) the **summary/recap sweep** â€” every slide whose title matches `Summary | Recap | Key Takeaways | Wrap[-]Up` must be addressed by a plan action OR have every surviving stale token listed in `intentionally_kept`; (c) the **notes-structure sweep** â€” any action using wholesale notes replacement (`old_speaker_notes` + `speaker_notes` without `notes_changes`) is rejected; (d) the **notes-OST coherence sweep** â€” any `notes_update` or `post_process_notes` action that introduces technical terms not present in the slide's OST or a companion OST action is rejected (Rule 34); (e) the **new-slide schema and content quality sweep** â€” every `add_new_slide` action must use a valid `slide_layout` from the six supported layouts, provide the layout-specific data field, not use `body`, and (for `cards`) use domain-specific headings rather than generic datasheet headings; (f) the **OST-review completeness check** (enforced by `validate_plan.py`, not `audit_gate`) â€” every `notes_update` action must carry a valid `ost_reviewed` value (`"consistent"` with `ost_review_note`, or `"companion_action_added"` with a qualifying OST companion action on the same slide). See "Mandatory Sweeps" and "Hard Schema Constraints" sections.
28. **Structural completeness â€” parallel sections must receive comparable depth.** When the deck dedicates a section to teaching concept X, and concept Y is a peer of X in the same conceptual grouping, Y must receive comparable depth. The grouping is not predefined â€” it emerges from the deck's own content structure and the source inventory. If the deck has dedicated slides for three controller types and a fourth exists in the portfolio, the fourth needs comparable coverage. If a source delta introduces a new protocol, transceiver family, security capability, or any other independently teachable concept, that concept needs coverage proportional to its importance â€” not just a bullet on a parent slide. During Phase 3, build a "section parity matrix" listing each parallel concept group discovered in the deck, the slides dedicated to each member, and the depth tier (dedicated slides vs. table row vs. notes-only mention vs. absent). Any member at a lower depth tier than its peers is an automatic `new_slide_candidate` finding unless explicitly justified as out-of-scope with documented reasoning.
29. **Summary slides must reflect the complete updated story.** After all content changes are planned (including new slides), re-read every summary/recap/key-takeaways slide and verify that its claims, bandwidth figures, protocol lists, and feature highlights cover the full scope of the deck â€” including newly added content. A summary that was correct before new slides were added is stale after them. Every `add_new_slide` action that introduces a new capability (new protocol, new bandwidth tier, new IP block) must trigger a dependent `update_existing` action on the nearest summary slide, or the plan is incomplete.
30. **"No feature changes" does not mean "no content changes needed."** A source that says "no feature changes between version X and version Y" confirms that existing claims remain correct â€” it does NOT justify skipping content gaps. A topic that exists in the product but is absent or under-represented in the deck is a content gap regardless of whether it changed between releases. Separately evaluate: (a) are existing claims still correct? (b) is the topic adequately taught? Both must be true to clear a slide.
31. **Decompose every source delta into independently teachable concepts.** Before the Phase 3 parity check, every source delta must be broken into its constituent concepts. A "source delta" is a change or addition from a source (e.g. "CPM6 added to Versal Premium Gen 2"). A "teachable concept" is a topic a learner would need a distinct explanation of. For each concept, record: (a) `concept`, (b) `parent_delta` â€” which source delta it came from, (c) `independently_teachable` â€” could this concept justify its own slide? Apply the test: "If a learner understood everything else in the deck but not this concept, would they have a meaningful knowledge gap?", (d) `current_coverage` â€” where/how the deck currently covers it (dedicated slide, table row, bullet, notes mention, or absent), (e) `adequate` â€” is current coverage sufficient given the concept's importance? Every concept tagged `independently_teachable: true` AND `adequate: false` is an automatic finding. Record the decomposition in the `concept_decomposition` array of the verification report. This step is what prevents treating "CXL 3.1" as merely a CPM6 feature bullet when it is a protocol that warrants its own teaching surface.
32. **Source deltas may introduce concepts that belong to categories not yet present in the deck.** A delta about controller X may introduce protocol Y, transceiver family Z, or security capability W. Each concept must be assessed in its own natural category, not constrained to the category of its parent delta. If the concept would create a new section that does not yet exist in the deck, that is a `new_slide_candidate` finding. Do not assume the deck's current section structure is complete â€” source deltas can reveal structural gaps.
33. **Documented parallelism groups 1, 2, and 4 are mandatory, not optional.** When two phases or operations are listed as safe to parallelize (no shared mutable state, outputs consumed only by later phases), they MUST be dispatched concurrently â€” using parallel tool calls (for MCP queries), parallel Bash calls (for independent scripts), or background agents. Sequential execution of independent phases wastes wall-clock time and is a process violation. The three mandatory groups are: (1) Phase 1.5 || Phase 2 â€” launch speaker notes extraction and source collection concurrently after Phase 1; (2) Phase 2 MCP queries â€” launch all NABU, Confluence, and JIRA queries as parallel tool calls in a single message; (3) Phase 5A || Phase 5B â€” launch apply-existing-updates and create-additions-deck concurrently after plan approval. Group 3 (concept decomposition) remains SHOULD â€” analytical reasoning benefits from holistic context where understanding one delta's concepts informs analysis of another.
34. **Speaker notes must not be the sole teaching surface for any new concept.** Notes elaborate, explain, and provide context for what is visible on screen â€” but they must not introduce a technical concept (protocol, IP block, spec, capability) that has zero corresponding mention in the slide's on-screen text (OST). If a `notes_update` or `post_process_notes` action introduces key terms that do not appear in either the existing OST or a planned OST-level action (`update_existing`, `fragment_replace`, `add_new_slide`) on the same slide, the plan is incomplete. `audit_gate.py` enforces this: for every notes-modifying action, it extracts technical terms from the replacement/new notes text and verifies each appears in the slide's current OST shapes or in a companion OST action targeting the same slide. A finding that says "slide only covers X â€” no mention of Y" is not adequately addressed by adding Y to the notes alone. The OST must at least reference Y (a bullet, a label, a callout, a table row) so learners see the concept before the instructor elaborates on it.
35. **Intra-slide term consistency â€” diagram labels must match bullet text and source canonical forms.** For every slide that contains both bullet/body text and diagram/grouped-shape labels, every technical term (processor name, IP block name, protocol name, interface name) must be consistent across all shapes on that slide. A bullet saying `A78AE` while a diagram label says `A78E` on the same slide is an automatic finding â€” even if one of them is correct. The audit must: (a) extract all technical terms from all shapes on the slide (including group-nested children â€” Rule 16), (b) compare each term against every other occurrence on the same slide for near-miss variants (edit distance <= 2, same semantic category), and (c) compare each term against the canonical form in `reference_extract.json`. Any mismatch is a finding with `type: "intra_slide_inconsistency"`. This check runs during Phase 3 per-slide audit, not as a post-apply gate â€” catching the error before planning prevents wasted execution time. The most common failure mode is a diagram label that abbreviates or misspells a processor/IP name while the surrounding bullets use the correct form.
36. **Before authoring any JSON artifact, read `references/artifact_schemas.md` â€” specifically the field-name quick reference table at the very top.** Never write field names from memory: `slide` is wrong, `slide_number` is correct; `action_type` is wrong, `type` is correct; `match` is wrong, `match_text` is correct â€” and so on for every alias in the table. This applies equally to subagents: every Agent tool prompt that asks for a JSON artifact **MUST** include this instruction verbatim: *"Read `references/artifact_schemas.md` field-name table before writing any JSON. The table is at the top of the file."* Subagents start with no parent context and will invent field names without this explicit instruction.
37. **Every `notes_update` action requires an explicit OST review outcome.** When speaker notes are updated on an existing slide, the author must document whether the on-screen text (OST) of that slide also needs updating. Set `ost_reviewed` on the action to one of two values: `"consistent"` â€” the existing OST already reflects the notes change; no OST action is needed. A non-empty `ost_review_note` explaining the alignment is required. `"companion_action_added"` â€” a companion `update_existing` or `fragment_replace` action targeting the same `slide_number` is present in the plan to update the OST. `validate_plan.py` rejects any `notes_update` action missing `ost_reviewed`, carrying an invalid value, using `"consistent"` without `ost_review_note`, or claiming `"companion_action_added"` when no qualifying companion action exists. `audit_gate.py` additionally warns when `ost_reviewed: "consistent"` but the Phase 3 finding recommended an OST-level action â€” verify the OST is truly unchanged before marking consistent.

38. **Generational analysis is mandatory for every slide clear.** Before marking any slide as `slides_explicitly_cleared`, the auditor must document: (a) what generation the slide's content belongs to, (b) what changed between that generation and the target (with `source_ids`), and (c) why those changes do not affect this slide. Clearing reasons that only reference mechanical scan results (e.g. "no stale terms found", "scan is clean", "content is still valid") are rejected by `audit_gate.py`. The `generational_analysis` object is required on every `slides_explicitly_cleared` entry — see `references/artifact_schemas.md` for the schema. A slide whose content is factually correct but incomplete (e.g. describes CPM5 without mentioning CPM6) is NOT clear — it has a content gap finding.

39. **Portfolio-scope slides require IP-block-level source queries.** When a slide is classified as an SoC overview, block diagram, or processing system diagram (typically 15+ shapes with named functional blocks), every functional block that carries a protocol name, spec value, or processor identifier is a "key technical component" that must be queried against sources — not just blocks related to the deck's primary topic. A memory solutions deck that shows a PCIe block must query for PCIe changes; a PCIe deck that shows DDR blocks must query for DDR changes. During Phase 2, extract the list of named functional blocks from each portfolio-scope slide and issue at least one batch NABU query covering all non-primary-topic blocks (e.g. "What changed in Gen 2 Versal for PCIe, OCM, APU, and RPU?"). Record which blocks were queried and which returned no changes in `source_inventory.json`. A portfolio-scope slide cannot be cleared unless every named functional block on it has been checked against sources. The most common failure mode is querying only the deck's stated theme (e.g. "memory") while ignoring architectural context blocks (PCIe, OCM, APU) that also appear on the same slide and have generational changes.

40. **Delta-tracing sweep — grep old spec values across all slides.** After Phase 2 source collection, for every source delta that identifies a changed specification (e.g. OCM 256 KB → 2 MB, line rate 32 GT/s → 64 GT/s, A72 → A78AE), grep `deck_extract.json` for the old value across ALL slides — not just slides thematically related to the delta's topic. A specification change discovered on one slide (e.g. slide 8 teaches OCM 2 MB) must be traced to every other slide that mentions the old value (e.g. slide 4 still says "256 KB"). Record each old-value hit as a candidate finding. This sweep runs during Phase 3, after the per-slide audit and before concept decomposition. It catches cross-slide inconsistencies that per-slide auditing misses because the auditor focused on the slide's primary topic rather than tracing every changed value deck-wide.

41. **Image-detection heuristic for OST review.** Before marking `ost_reviewed: "consistent"` on a `notes_update` action, verify that the slide's on-screen content is actually represented in `deck_extract.json` text shapes. If the speaker notes describe a table, diagram, or feature matrix but `deck_extract.json` shows fewer than 4 text shapes (excluding title, authoring markers, and slide-number labels), the visible content is likely an embedded image that the text extraction cannot see. In this case: (a) flag the slide as `image_limited` in the action's `ost_review_note`, (b) document which concepts from the notes update cannot be verified against OST because the OST is an image, and (c) add a `manual_review_required` note in the action specifying what the image should be checked for. Do NOT mark `ost_reviewed: "consistent"` with a generic note — the note must explicitly acknowledge the image limitation and list the unverifiable concepts. This prevents false "consistent" claims on slides where the real teaching content is baked into a non-editable image.

## Rule 49 - Theme palette extraction is mandatory for new slides

Every Phase 5B builder must read `ppt/theme/theme1.xml` from the base deck
and apply the deck's actual scheme colors. Hardcoded brand colors and
python-pptx defaults are hard failures at visual review.
See `references/new_slide_guide.md` - "Theme Color Extraction".
